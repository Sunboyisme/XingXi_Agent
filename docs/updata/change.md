#### 安装后无法打开的修复

初始安装包在 8766 端口已有其他 Bai 数据空间运行时，启动钩子返回错误，桌面程序以 101 退出，没有显示可用窗口。已在 `C:\APP\Bai Agent` 的原安装程序上捕获并复现；原发布验证使用隔离端口，漏掉了默认端口冲突场景。

修复后自动选择可用端口；在启动子进程前保留端口，防止界面和后端选择不同地址。三个 Rust 回归测试覆盖空闲端口预留与释放、其他服务占用、同一空间服务复用。原生检查分别覆盖其他 Bai 服务占用、普通 HTTP 服务占用、同一空间服务复用，均从内嵌页面通过 IPC 连接后端，七个认证接口返回成功，无检查期间页面脚本错误；退出应用没有关闭不属于它的服务。

已备份原安装目录，再用修正版 NSIS 实际更新 `C:\APP\Bai Agent`。安装后的程序除 Tauri 的 NSIS 类型标记外与修复构建一致；在不覆盖后端端口或数据目录的情况下成功打开，自动使用 62248 端口，与仍占用 8766 的开发后端共存。正常安装数据目录令牌和 IPC 返回的令牌一致，七个本机接口通过认证检查。用户已在设置页操作，因此保留窗口，本轮未重新启动这个正常数据空间，也没有改动模型配置或调用真实模型。

修正版仍为 0.1.0。初始安装包已归档至交付目录的时间戳子目录；原 Git 标签 `v0.1.0` 保留，修复源代码另存为 `v0.1.0-fix.1`。本轮证据和程序备份在 `.local-data/startup-repair/`，均不进入 Git。

### 历史技术评估（建议，不代表已接入） · 小汐接入 Deep Agents 的判断

来源：[docs/deep-agents-assessment.md](../deep-agents-assessment.md)。

评估日期：2026-10-17。此记录评估接入方式，当前代码仍使用 `create_agent`。

可以接入，也适合未来增加复杂任务能力；当前日常聊天、天气、提醒和微信消息，用现有 Agent 已能完成，换框架本身不会让这些功能更简单。

#### 现有边界

- `backend/app/agent.py` 使用 LangChain `create_agent`，通过 `prepare_tools` 加载内置工具及 MCP 工具，输出消息流、工具记录和 token 用量。
- 聊天历史从 SQLite 读取最近 24 条消息；确认后的个人记忆从现有数据库注入。
- 学习流程通过独立 LangGraph 图及 SQLite checkpoint 维护练习和恢复状态。
- 微信登录、消息去重、投递状态和定时提醒属于渠道与应用服务，需要继续由这些服务负责。

#### 能省下的工作

Deep Agents 基于 LangChain / LangGraph，提供文件上下文管理、子任务委派、历史压缩及 Skills 等能力。需要“查多份资料 → 拆解任务 → 分步处理 → 输出文件”时，可以减少自己组装这些能力的工作。任务规划可按所选版本显式启用。

对简单聊天，这些额外能力也可能增加提示词、工具数量、模型调用与调试成本；实际效果取决于模型的工具调用表现，不能仅凭框架名称判断。

#### 建议接入顺序

1. 保留 FastAPI、Tauri、SQLite、MCP 管理、学习图与微信服务，抽出聊天 Agent 的构建入口。
2. 给复杂任务增加可切换的 Deep Agents 执行路径，日常消息沿用现有路径；用同一套 `prepare_tools` 保持工具开关与权限行为一致。
3. 在独立任务目录配置文件后端；通过现有记忆服务读取和写入用户记忆，避免出现第二套互不一致的持久记忆。
4. 适配任务、子任务和工具事件到现有 SSE 协议，并验证停止、失败恢复、最终答案去重与 token 统计。
5. 锁定兼容依赖后，对比实际模型下的成功率、调用次数、耗时和成本，再决定是否统一入口。

不能只把 `create_agent` 改成 `create_deep_agent` 就视为迁移完成。依赖兼容、流式事件、持久状态、工具边界和桌面后端封装都需要验收。

官方参考：[Deep Agents 概览](https://docs.langchain.com/oss/python/deepagents/overview)、[定制与中间件](https://docs.langchain.com/oss/python/deepagents/customization)。

#### 0.1.4加入写文档读文档的功能：

请为 XiaoXi Agent 实现“上传资料 → 显示解析状态 → 按需读取 → 生成结果文件 → 预览、下载或另存为”的办公文件处理能力。先检查项目现有架构、AGENTS.md，以及附件上传、工具注册、技能脚本和文件产物的实现，优先复用现有能力，渐进修改。

本轮范围是：用户主动上传资料，小汐根据需求读取、整理并生成新文件，保留上传原件；暂不实现本地文件夹管理、任意路径读写或通用代码执行。应用功能负责选择和拖入文件、展示文件名及解析状态、预览结果、下载和通过系统窗口另存为；后端服务负责存储、解析、格式生成、权限校验和任务状态；模型通过内置工具调用这些能力。建议提供 list_files、read_file、create_document、create_spreadsheet、create_text_file，具体命名可遵循项目现有约定。模型使用文件编号访问当前对话授权的附件，不直接指定电脑上的任意绝对路径。

输入优先支持 Word（.docx）、带文字层的 PDF、TXT、MD、CSV、JSON；解析时尽量保留页码、段落和表格来源，支持按页码或片段读取，并明确展示上传中、解析中、可读取、部分解析和失败状态。扫描 PDF、加密文件、损坏文件及暂不支持的内容应给出真实、清楚的提示，不能把解析失败当成空白内容，也不能编造原文。文件内容是待处理资料，不能成为新增权限或执行操作的指令。

输出支持 Word（.docx）、PDF、Excel（.xlsx）、TXT、MD、CSV、JSON。模型负责组织内容与结构，程序使用相应文件库生成合法文件，禁止仅修改扩展名冒充目标格式。Word 支持基本标题、段落、列表、表格、图片和分页；PDF 保证中文字体与基本排版；Excel 支持多工作表、数据、基本公式、数字格式和样式；CSV 正确处理编码、引号与换行；JSON 必须通过结构校验。第一版重点是根据资料生成新文件，暂不承诺完整保留复杂原始版式、宏、批注或修订。解析时不执行文档中的宏、脚本或公式。

生成结果应在对话中展示文件卡片，提供适合格式的文档、表格或文本预览，以及下载、另存为入口；预览转换失败应明确说明，并保留原始产物。支持一次任务生成多个文件。所有上传副本和生成文件存储在应用管理的区域，执行文件类型、内容、大小、处理时长和会话归属校验；默认生成新文件或新版本，不静默覆盖原文件。另存为的位置由用户通过系统窗口选择，覆盖已有文件时明确确认。处理失败、取消或重试时，不展示虚假的成功状态，也不遗留可见的半成品。

### 需求与实施计划原文（不代表全项验收） · XiaoXi 复杂任务能力优化计划

来源：[docs/updata/0.1.5/0.1.5添加复杂任务.txt](0.1.5/0.1.5添加复杂任务.txt)。

#### 一、目标与已确定的交互

让 XiaoXi 自动组织多步骤任务，保存中间成果，支持执行中补充要求和中断后继续。

- **全自动进入**：在现有聊天框表达需求，由模型识别并规划，不增加手动模式开关。普通问答和简单工具请求继续使用现有流程。
- **覆盖全部现有工具**：内置工具、文件生成、生图、MCP、Skills、记忆、日历和学习工具统一接入任务执行机制，沿用已有开关与授权。
- **支持执行中补充**：新消息先保存，当前工具调用结束后处理补充要求，再执行后续操作。
- **重启后等待继续**：恢复任务和成果，收到“继续”等明确指令后才重新调用模型或工具。
- 复用现有 Agent、SQLite 和流式事件机制；第一版由一个执行器顺序推进步骤。

#### 二、任务组织与持久化

##### 自动识别和规划

使用当前选定的聊天模型识别普通请求、新任务、继续任务及修改要求；多阶段交付自动建立任务。识别和规划产生的调用纳入用量统计。

每个任务保存目标、约束、输入资料、预期成果、完成条件和模型选择。步骤保存依赖关系、状态、来源引用和输出摘要。关键信息缺失时提问，信息充分时直接执行。

##### 按步骤执行和保存

新增任务、步骤、操作记录三类持久数据，通过增量迁移保留现有数据。每次运行关联稳定任务编号，继续执行时创建新的运行记录，并复用该任务的历史成果。

执行器按依赖顺序推进；每次工具调用前保存操作编号，调用后保存实际结果、产物编号及错误。步骤完成必须有对应结果，不能仅依据模型的完成声明。

任务上下文使用已保存的要求、来源和步骤成果；长资料按需读取。文件沿用现有产物区，原始附件不覆盖，修改后的文件保留新版本。

##### 执行中调整

补充消息按到达顺序处理，在下一次工具调用前更新任务版本并重新规划。保留仍然有效的成果，只重做受影响的步骤及其后续步骤。

工具执行绑定明确的任务版本和用户消息，避免运行中新增消息改变当前操作的授权依据。已完成的外部操作保留真实记录，不因重新规划而被当作尚未执行。

#### 三、恢复、重复操作与完成判定

- **已完成操作**：通过稳定操作编号复用结果，区分续跑与用户新提出的重复请求；引用产物前检查文件仍然存在。
- **读取和计算**：临时失败最多自动重试一次，再失败则保存进度并说明原因。
- **本机写入和文件生成**：补齐跨运行的操作去重，结合业务记录或产物判断是否已经完成。
- **生图、MCP、技能脚本**：调用中断且结果不明时先核对已有结果；无法核对则暂停并说明，不能把“继续任务”当作重新提交该操作的授权。MCP 和脚本默认不作可安全重试的假设。
- **停止与重启**：停止后保留成果；服务重启时将未完成任务恢复为暂停状态，并区分明确失败与结果未知，不自动重发外部操作。
- **等待用户**：缺少信息、需要沿用已有确认流程或结果无法核实时，任务进入等待状态；收到答复后继续。
- **交付核对**：按完成条件核对实际文件、操作记录和资料来源。存在未完成的必需步骤时，明确展示已完成与待处理内容，不标记整个任务完成。

沿用现有单次运行的时间限制和工具自身限制；超时后保留进度，等待用户继续。

#### 四、聊天界面与接口

聊天中增加可展开的任务卡，显示任务目标、当前步骤、已保存成果、等待原因和继续入口。详细工具记录仍可展开查看，不显示虚构百分比。

复杂任务运行时允许发送文字及附件，输入区提示“补充当前任务要求”，保留停止操作。补充提交后显示“已收到，当前步骤结束后处理”，不另开并发执行器。

接口调整：

- `RunRead` 增加可选的 `task_id`；任务状态与单次运行状态分别保存。
- 新增会话任务列表、任务详情、继续和结束任务接口。
- 现有消息接口支持保存执行中的补充消息；自然语言“继续”与任务卡入口使用同一恢复逻辑。
- 现有 SSE 增加任务、步骤和要求更新事件，携带任务编号及版本；重新打开对话后从持久数据恢复展示。

保留普通聊天、学习流程及现有微信文字收发兼容。微信复用任务执行与最终文字回执，完整步骤和文件在桌面查看。

#### 五、实施顺序与验收

按以下顺序完成本轮优化：

1. **任务数据与执行基础**：迁移、自动识别、规划、步骤保存和统一操作记录。
2. **工具恢复与去重**：接入全部现有工具，处理成功复用、失败、结果未知和权限变化。
3. **聊天交互**：任务卡、实时状态、执行中补充及自然语言继续。
4. **交付整理**：完成核对、数据导出导入兼容、更新说明及验收步骤。

重点验收场景：

- 普通问答正常；多阶段请求自动建立任务。
- 多份资料生成 Excel 和 Word；Word 失败后继续，保留已有 Excel。
- 生成图片成功后聊天连接断开，继续时展示原图，不重复生成。

- 执行中修改预算，只更新受影响的计算和报告。

- 任务执行期间关闭工具或撤销脚本授权，后续调用立即遵守当前设置。
- 已有日历、记忆及学习确认规则继续生效；历史对话与数据导出导入保持兼容。
